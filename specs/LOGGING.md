# Logging Handoff for `explore-jira-agent-assignment`

This file describes what the live `explore-jira-agent-assignment` app should
implement to prove the Remote Logging Extension design. The vendored snapshot
under `specs/explore-jira-agent-assignment` is reference evidence only; do not
edit it in this repository.

## Goal

Use app-local structured logs to make two behaviors visible:

- Remote behavior: request authentication and Remote Invocation Contract
  matching.
- A2A behavior: provider-neutral remote-agent signals becoming A2A-visible
  events and stream envelopes.

The app should own the actual logger, request lifecycle, and content-safety
policy. The helper library design only supplies event names, summary shapes, and
redaction requirements.

## Required Log Events

Implement these events from
[`remote-logging-extension-design.md`](./remote-logging-extension-design.md):

| Event | Required for the app | Notes |
| --- | --- | --- |
| `remote.auth.accepted` | Yes | Emit after Forge Remote request validation succeeds. |
| `remote.auth.rejected` | Yes | Emit when authentication returns Problem Details. |
| `remote.invocation.matched` | Yes | Emit after the route's Remote Invocation Contract matches. |
| `remote.invocation.mismatched` | Yes | Emit when a verified request does not satisfy the route contract. |
| `remote.a2a.signal.mapped` | Yes | Emit for each mapped Remote Agent Signal in the demo flow. |
| `remote.a2a.stream.encoded` | Yes, for streaming routes | Emit after encoding an A2A JSON-RPC stream envelope. |
| `remote.a2a.completed` | Yes | Emit when the task reaches a terminal state. |

## Record Fields

Each log record should be a structured object with at least:

- `event`
- `level`
- `message`

Include these when available:

- `requestId`: generated at the HTTP boundary or copied from JSON-RPC `id`.
- `traceId`: copied from `x-b3-traceid`.
- `spanId`: copied from `x-b3-spanid`.
- `timestamp`: generated by the app logger or explicitly recorded.
- `remoteContext`: a Safe Remote Context Summary.
- `invocation`: route contract name, authentication kind, and required token
  presence requirements.
- `a2a`: signal category, mapped event kind, task state, final flag, task id,
  context id, stream response kind, and artifact id/name when available.
- `problem`: Problem Details fields, without raw causes or stack traces.

## Safe Context Summary

Do not log the raw `ForgeRemoteContext`. Implement a local summary that matches
the design:

```ts
{
  verification: {
    audience,
    issuer
  },
  fit: {
    appId,
    principalSubject
  },
  forwardedTokens: {
    hasSystemToken,
    hasUserToken
  }
}
```

Rules:

- `appId` is present only when `context.fit.app.id` is a string.
- `principalSubject` is present only when `context.fit.sub` is a string.
- Forwarded token values are never logged.
- Raw Authorization headers are never logged.
- Unknown FIT claims are never logged.
- Request bodies, message parts, and artifact contents are not logged by
  default.

The demo may opt into logging scenario-authored message previews because those
fixtures are intentionally safe demonstration data. That opt-in should stay
local to the app and should not become the extension default.

## Example Records

Authentication success:

```json
{
  "event": "remote.auth.accepted",
  "level": "info",
  "message": "Forge Remote request authenticated",
  "requestId": "request-1",
  "traceId": "b3-trace",
  "remoteContext": {
    "verification": {
      "audience": "ari:cloud:ecosystem::app/example",
      "issuer": "forge/invocation-token"
    },
    "fit": {
      "appId": "ari:cloud:ecosystem::app/example",
      "principalSubject": "ari:cloud:jira::site/example-user"
    },
    "forwardedTokens": {
      "hasSystemToken": true,
      "hasUserToken": true
    }
  }
}
```

A2A signal mapping:

```json
{
  "event": "remote.a2a.signal.mapped",
  "level": "info",
  "message": "Remote Agent signal mapped to A2A event",
  "requestId": "request-1",
  "a2a": {
    "signalCategory": "approval-needed",
    "mappedKind": "task-state-update",
    "state": "auth-required",
    "final": false,
    "taskId": "task-1",
    "contextId": "context-1"
  }
}
```

Terminal outcome:

```json
{
  "event": "remote.a2a.completed",
  "level": "info",
  "message": "A2A task reached terminal state",
  "requestId": "request-1",
  "a2a": {
    "state": "completed",
    "final": true,
    "taskId": "task-1",
    "contextId": "context-1"
  }
}
```

## Acceptance Criteria

- Logs tell one request story from authentication through invocation contract
  matching and A2A completion.
- Logs use the exact event names from this file.
- Logs include request correlation where available.
- Logs show token presence but never token values.
- Logs show the principal subject only as an identifier.
- Logs do not dump arbitrary FIT claims or raw request objects.
- A2A logs show signal category, mapped event kind, state, finality, and stream
  encoding points without requiring a separate event model.
- The demo implementation remains app-local until the Remote Logging Extension
  API has been proven by this example.
